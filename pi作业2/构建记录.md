# 真实构建记录与问题清单

本文件记录 2026-11-23 在本机对本仓库做的真实构建, 命令输出留档在同目录 构建日志 下。

## 一 环境

1. 系统为 Windows, Node 为 v24.14.0, npm 为 11.9.0。
2. 仓库为 main 分支, 提交 c3cc91632d0a1950fb122605b190233f2aa0006e, 构建前工作区干净。
3. 依赖按 package-lock.json 安装, 关键工具版本为 typescript 7.0.2, esbuild 0.28.2, @types/node 22.19.19。
4. 网络情况与直觉不同。PowerShell 的 Invoke-WebRequest 与 Resolve-DnsName 直连超时, 但 Node 的 fetch 可以访问 registry.npmjs.org 与 registry.npmmirror.com 与 models.dev。npmjs 单次请求约 7.5 秒, npmmirror 约 0.6 秒。

## 四 问题清单

1. PowerShell 执行策略拦截 npm 与本地脚本。
   1. 现象为 `无法加载文件 ... npm.ps1, 因为在此系统上禁止运行脚本`, node_modules/.bin 下的 tsc.ps1 同样被拦。
   2. 影响是直接敲 `tsc` 会命中 .ps1 垫片而失败, 看起来像工具没装。
   3. 处理方式为改用 npm.cmd, 脚本用 `Set-ExecutionPolicy -Scope Process Bypass` 执行, 编译统一走 `npm run build` 由 cmd 调用 tsc.cmd。
2. .npmrc 里是 pnpm 的配置, npm 每次调用都告警。
   1. 现象为 `Unknown project config "min-release-age"` 与 `min-release-age-exclude`, 每次命令输出两行以上。
   2. 原因是仓库默认用 pnpm, 这两个键 npm 不认识。
   3. 影响仅为噪声, 但说明用 npm 装依赖属于旁路, 与仓库默认流程不一致。
3. 直连 npmjs 安装极慢, 表现为卡死。
   1. 现象为首次 `npm install` 运行约 20 分钟, 缓存与 node_modules 都无增长。
   2. 原因是 npmjs 在本机可达但每次请求约 7.5 秒, 解析上千个包时退化为几乎停滞。
   3. 处理为换 npmmirror 镜像, 同样一次安装 184 秒完成。
4. 本机 npm 缓存不能支撑离线安装。
   1. 现象为 `npm install --offline` 依次缺少 marked 18.0.14, zod 4.6.7, @silvia-odwyer/photon 0.3.3, @google/genai 2.32.0。
   2. 审计结果为 222 个运行期 tarball 中有 93 个不在缓存。
   3. 原因是缓存来自另一个旧版 pi 检出的安装, 版本号对不上。
   4. 结论为本机无法离线复现构建, 必须联网。
5. `--omit=dev` 没有跳过工作区的 devDependencies。
   1. 现象为加了 `--omit=dev` 仍然去取 schema 的 devDependency zod 4.6.7。
   2. 影响是"只装运行期依赖"不能靠参数实现, 只能改 package.json 清单。
6. 编译依赖 devDependencies 里的类型包。
   1. 现象为临时删掉各包 devDependencies 后, chord 报 `TS7016 Could not find a declaration file for module 'ws'` 与 `TS2307 Cannot find module 'react'`, mcp 报 `TS7016 ... 'cross-spawn'`。
   2. 结论是 tsc 阶段需要 @types/react 与 @types/ws 与 @types/cross-spawn 与 react 本身, 构建不是只装 dependencies 就能完成。
7. 镜像里的 typebox 包残缺, 直接导致根构建失败。
   1. 现象为首次 `npm run build` 在最后一步退出码 2, coding-agent 报 60 余条 `TS2307 Cannot find module 'typebox'`, 并连带出大量 implicit any 错误。
   2. 原因是 npmmirror 的 typebox@1.3.27 压缩包里只有 .mjs, 没有 package.json 声明的 build/index.d.mts 等声明文件, 而 npmjs 的同版本包有。
   3. 处理为用 Node 直接下载 npmjs 的 typebox-1.3.27.tgz 覆盖 node_modules/typebox, 单包重建 18.6 秒通过。
   4. 建议为用镜像装完依赖后抽查关键包的声明文件, 不要默认镜像包与官方一致。
8. ai 的生成阶段没有超时也没有进度输出。
   1. 现象为日志停在 `Fetching models.dev catalog...` 后长时间不动, 慢网络或并发下载时更明显。
   2. 原因是 catalog 抓取用 fetch 但没有超时参数。
   3. 影响是构建看起来卡死, 实际在等网络, 容易误判为代码问题。
9. 根构建的 cd 链在 Windows 正常。
   1. 现象为 `cd ../schema` 一站站执行成功, 没有路径分隔符问题。
   2. 结论是报告所称"写死的 cd 链"在 cmd 下成立。
10. 构建会重写受版本控制的生成文件。
    1. 现象为 src/models.generated.ts 与 src/providers 下 43 个 *.models.ts 每次构建被重新生成, src/providers/data 被 .gitignore 忽略。
    2. 本次生成后 `git status` 干净, 说明生成结果与提交一致, 是确定性的。
    3. 风险是上游目录变化时会产生大量 diff, 提交前应单独核对。
11. 首次失败会留下前 10 个包的 dist。
    1. 现象为根构建在 coding-agent 失败时, 其余 10 个包的 dist 已经齐全。
    2. 影响是不能用"dist 是否存在"判断构建成功, 只能看退出码。
12. env 的 daemon 与 tui 的 native 确实不在默认构建内。
    1. 现象为构建后 packages/env/bin 仍不存在, packages/tui/native 下的 .node 仍是仓库自带文件。
    2. 本机未装 cargo, `build:daemon` 无法运行, 与报告所述一致。

## 五 与报告结论的对照

1. 构建顺序与产物与报告第一节的表格一致, 11 个包的 dist 内容与各包 exports 对应。
2. ai 的三段得到确认, 生成阶段联网抓上游, 校验阶段输出 `Generated model data is valid.`, 编译后 data 被拷进 dist/providers/data。
3. coding-agent 的三段得到确认, tsc 与可执行位与资产拷贝之后, bundle 输出 84 个文件 9.4 MiB, 启动器指向 dist/bundle/cli.js。
4. 根构建链是写死的 cd 链这一点被实际执行验证, 顺序与依赖图的拓扑序一致。
5. `build:offline` 与 `build` 的唯一差别得到确认, 离线变体日志里没有一次 Fetching, 用时反而更短。
6. 依赖图与层级划分没有被构建结果推翻, 十一个包的编译只依赖更低层的 dist 与自身 dependencies, 未出现反向依赖导致的失败。
